### Decoupled Points (Critical Architectural Wins)

1. **File System Abstraction**
   - **Before:** 15+ direct `fs.readFileSync`/`fs.writeFileSync` calls scattered across modules
   - **After:** All I/O goes through `StorageAdapter` interface
   - **Impact:** Zero filesystem dependencies in cloud; MongoDB handles all persistence

2. **Singleton Elimination**
   - **Before:** `JobStateService` and `EmailNotifier` were module-level singletons
   - **After:** Factory functions (`createJobStateService`, `createEmailNotifier`)
   - **Impact:** No state leakage across Cloud Run warm container starts

3. **Graceful Error Handling**
   - **Before:** `process.exit(1)` in `linkedin_client.js` killed the container
   - **After:** `LinkedInAuthChallengeError` thrown, caught by orchestrator
   - **Impact:** Orchestrator can send critical alert email before graceful shutdown

4. **Configuration Decoupling**
   - **Before:** `companiesConfig.js` directly read 3 files (`fs.readFileSync`)
   - **After:** `loadCompaniesConfig(storageAdapter)` delegates to adapter
   - **Impact:** MongoDB pre-seeded; no CSV parsing in production

## 🎯 Core Achievements (Technical Deep Dive)

### 1. State Changes: StorageAdapter Pattern

**WHAT Changed:**
- Created `services/storage/StorageAdapter.js` abstract interface
- Implemented `FileStorageAdapter.js` (wraps all existing `fs` logic)
- Implemented `MongoStorageAdapter.js` (MongoDB native driver)
- Factory function `createStorageAdapter()` auto-selects based on `STORAGE_BACKEND` env var

**WHY Important:**
- **Dependency Injection:** Storage backend is now injectable, making the system testable
- **Cloud Compatibility:** Zero filesystem dependencies in production
- **Backward Compatibility:** Local dev still works via `FileStorageAdapter`

**Architectural Impact:**
- **Separation of Concerns:** Business logic no longer knows about filesystem paths
- **Testability:** Can inject mock adapters for unit testing
- **Scalability:** MongoDB handles concurrent writes, connection pooling
- **Maintainability:** Single source of truth for storage operations

**Files Changed:**
- `services/storage/StorageAdapter.js` (NEW - 97 lines)
- `services/storage/FileStorageAdapter.js` (NEW - 442 lines)
- `services/storage/MongoStorageAdapter.js` (NEW - 324 lines)
- `services/storage/index.js` (NEW - 38 lines)
- `scraper.js` (refactored - removed `loadSeenJobIds`/`saveSeenJobIds`, uses adapter)
- `ats/orchestrator.js` (refactored - passes adapter to workers)
- `ats/workers/comeetWorker.js` (refactored - accepts adapter, uses `writeRunLog`)
- `ats/workers/greenhouseWorker.js` (refactored - accepts adapter, uses `writeRunLog`)
- `ats/config/companiesConfig.js` (refactored - thin wrapper around `adapter.loadCompanies()`)

### 2. Logic Changes: Factory Pattern (Singleton Elimination)

**WHAT Changed:**
- `JobStateService`: Removed module-level singleton, added `createJobStateService(storageAdapter)` factory
- `EmailNotifier`: Removed module-level singleton, added `createEmailNotifier()` factory
- `JobStateService.loadHistory()`: Now async, always loads fresh (removed `this.loaded` guard)
- `JobStateService.persistState()`: Now async, uses `storageAdapter.persistSentHistory()`

**WHY Important:**
- **Cloud Run Warm Containers:** Module-level singletons retain state across invocations
- **State Leakage Prevention:** Each run gets a fresh `JobStateService` instance
- **Dependency Injection:** `JobStateService` now requires `StorageAdapter` (explicit dependency)

**Architectural Impact:**
- **Stateless Design:** Services are created per-invocation, no shared mutable state
- **Testability:** Can inject mock storage adapters
- **Predictability:** No hidden state that persists across runs

**Files Changed:**
- `services/JobStateService.js` (refactored - factory pattern, async methods)
- `services/EmailNotifier.js` (refactored - factory pattern)
- `ats/orchestrator.js` (refactored - uses factories in `run()` function)

### 3. Refactors: Graceful Error Handling

**WHAT Changed:**
- Created `LinkedInAuthChallengeError` class in `linkedin_client.js`
- Replaced `process.exit(1)` calls (lines 115, 139) with `Promise.reject(new LinkedInAuthChallengeError(...))`
- Updated `scraper.js` catch block to handle `LinkedInAuthChallengeError`
- Updated `orchestrator.js` catch block to send critical alert email on auth challenge
- Replaced standalone `process.exit(1)` in `scraper.js` with `process.exitCode = 1`

**WHY Important:**
- **Cloud Compatibility:** `process.exit(1)` kills the container mid-execution
- **Graceful Shutdown:** Orchestrator can catch errors, send alerts, persist state
- **Observability:** Errors are logged and reported before shutdown

**Architectural Impact:**
- **Error Propagation:** Errors flow through promise chains instead of killing the process
- **Recovery:** Orchestrator can handle partial failures (e.g., LinkedIn fails but ATS succeeds)
- **Monitoring:** Critical alerts are sent before shutdown

**Files Changed:**
- `linkedin_client.js` (error class, removed `process.exit(1)`)
- `scraper.js` (catch block updated, `process.exitCode = 1`)
- `ats/orchestrator.js` (catch block updated, sends critical alert)

### New Insights

1. **MongoDB Handles CSV/JSON Merging Seamlessly:** The `companies` collection is pre-seeded via migration script. `MongoStorageAdapter.loadCompanies()` simply queries the collection - no CSV parsing needed in production.

2. **Connection Pooling Works Well:** `MongoStorageAdapter` uses lazy initialization and connection pooling (maxPoolSize: 10). The connection stays open for the duration of the run, improving performance.

3. **Bulk Write Operations:** Both adapters use bulk write operations for efficiency. `MongoStorageAdapter` uses `bulkWrite()` with `upsert: true` for idempotency.

4. **Windows Compatibility:** `FileStorageAdapter` sanitizes timestamps (replaces colons with dashes) and ensures directories exist before writes.

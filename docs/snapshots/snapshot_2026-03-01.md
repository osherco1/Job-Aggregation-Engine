## 2. Current Phase Status

**Phase: Production Stabilization (Post-Deployment Day 5)**

The v6.1 deployment (snapshot_2026-02-24) introduced the Calibration DB Architecture, fail-fast persistence, and deterministic Workday IDs. However, during a Gemini-assisted deep analysis on 2026-03-01, **three additional critical issues were identified** through an external MongoDB forensics review:

1. **`calibration_rejected` duplicate insertion** — the same dropped jobs were re-inserted as brand new documents on every run (no dedup key), causing the collection to grow at ~6.7MB/day with 60-day TTL → ~400MB steady state.
2. **Timestamp overwrite bug** — `firstSeenAt` and `sentAt` were inside `$set` instead of `$setOnInsert`, causing every existing document's creation date to be overwritten on every run, making TTL-based cleanup unreliable.
3. **Zombie collections resurrected by stale Cloud Run deployment** — the local code was refactored but Cloud Run was still running the pre-refactor Docker image from Feb 24, continuously recreating `run_logs` and `enriched_jobs` in Atlas.

This session performed a **three-pronged refactor** (dedup noise elimination, timestamp fix, legacy eradication) and then **deployed the new code to Cloud Run** via `gcloud run jobs deploy` from Cloud Shell.

## 3. Core Achievements (Technical)

### 3.1 Issue 1: Silent Dedup for Already-Known Jobs

**What changed:** ATS workers (Comeet, Greenhouse) now receive a pre-loaded set of `knownJobIds` and silently skip any job already in `ats_sent_history` before running any filter logic.

**Why:** Without this, the same ~700 dropped jobs were written to `calibration_rejected` via `insertMany` on every single run. With 32 runs/day and 60-day TTL, this alone could accumulate ~400MB. The calibration collection should only contain genuinely new rejections, not dedup noise.

**Where in code:**

| File | Function/Section | Change |
|---|---|---|
| `ats/orchestrator.js` → `run()` | Pre-parallel phase | `const knownJobIds = await storageAdapter.loadSentHistory()` — loaded once before parallel execution |
| `ats/orchestrator.js` → `runAtsWorkers()` | Signature | Accepts `knownJobIds` parameter; passes to `processBatch()` |
| `ats/orchestrator.js` → `processBatch()` | Signature + call | Accepts `knownJobIds`; passes to `worker.fetchAllJobs(company, knownJobIds)` |
| `ats/workers/comeetWorker.js` → `fetchAllJobs()` | Signature + loop | Accepts `(company, knownJobIds)`; at top of raw-job loop: builds `jobId`, checks `knownJobIds.has(jobId)`, increments `stats.skippedDedup`, continues |
| `ats/workers/greenhouseWorker.js` → `fetchAllJobs()` | Signature + loop | Same pattern as Comeet |

**Impact:** Dramatic reduction in `calibration_rejected` writes. Only genuinely new jobs that fail business-logic filters (Location Gate, ATS Guard, Structured Gate) are written.

### 3.2 Issue 2: Timestamp Overwrite Fix

**What changed:** MongoDB `$set` / `$setOnInsert` operators corrected in `saveSeenJobIds()` and `persistSentHistory()`.

**Why:** Original code placed `firstSeenAt`, `sentAt`, and `createdAt` inside `$set`, causing every document's creation timestamp to be overwritten to the current time on every run. This made it impossible for future TTL indexes to clean old data correctly — every document appeared "fresh."

**Where in code:**

| File | Function | Before | After |
|---|---|---|---|
| `MongoStorageAdapter.js` → `saveSeenJobIds()` | `$set` block | `source`, `lastSeenAt`, ~~`firstSeenAt`~~, ~~`createdAt`~~ | `$set`: `source`, `lastSeenAt` only |
| `MongoStorageAdapter.js` → `saveSeenJobIds()` | `$setOnInsert` block | _(did not exist)_ | `$setOnInsert`: `firstSeenAt: now`, `createdAt: now` |
| `MongoStorageAdapter.js` → `persistSentHistory()` | `$set` block | `lastUpdatedAt`, `...metadata`, ~~`sentAt`~~, ~~`createdAt`~~ | `$set`: `lastUpdatedAt`, `...metadata` only |
| `MongoStorageAdapter.js` → `persistSentHistory()` | `$setOnInsert` block | _(did not exist)_ | `$setOnInsert`: `sentAt: now`, `createdAt: now` |

**Impact:** Creation timestamps are now immutable after first insert. This enables reliable TTL-based cleanup in future.

### 3.3 Issue 3: Complete Eradication of Legacy Collections

**What changed:** All code paths that could write to `run_logs` or `enriched_jobs` were permanently deleted — not gated behind `NODE_ENV`, but removed entirely.

**Why:** The previous v6.1 refactor introduced a `NODE_ENV === 'production'` gate in `writeRunLog()`. This worked in Cloud Run (where `NODE_ENV=production` is set in the Dockerfile) but failed in local development (where `.env` does not set `NODE_ENV`). Local `npm run ats` runs connected to the same Atlas cluster and pumped hundreds of `runtime`, `error`, and `raw` documents into `run_logs`, and LinkedIn scraper runs wrote to `enriched_jobs`. Additionally, the stale Cloud Run container (last deployed Feb 24) was still running pre-refactor code and recreating both collections on its scheduled runs.

**Where in code:**

| File | Change |
|---|---|
| `MongoStorageAdapter.js` → `this.collections` | **Removed** `RUN_LOGS` and `ENRICHED_JOBS` constants. Only 6 collections remain. |
| `MongoStorageAdapter.js` → `writeRunLog()` | **Hardcoded gate**: `if (type !== 'summary') { return; }`. No `NODE_ENV` check. Summaries route to `run_summaries` only. |
| `MongoStorageAdapter.js` → `writeEnrichedJobs()` | **Deleted entirely** |
| `StorageAdapter.js` → `writeEnrichedJobs()` | **Deleted** abstract method |
| `FileStorageAdapter.js` → `writeEnrichedJobs()` | **Deleted** implementation |
| `scraper.js` | **Removed** the `writeEnrichedJobs` call block and the `writeRunLog({ type: 'filtered' })` block |
| `comeetWorker.js` → `logRuntime()` | **Console-only**: no DB write. Only prints when `!QUIET_MODE` or `level === 'ERROR'` |
| `comeetWorker.js` → `saveRawResponse()` | **Console-only**: `console.log` when `DEBUG_COMEET=true` |
| `comeetWorker.js` → `saveErrorInfo()` | **Console-only**: `console.error` with serialized error info |
| `greenhouseWorker.js` → `logRuntime()` | Same as Comeet — console-only |
| `greenhouseWorker.js` → `saveRawResponse()` | Same as Comeet — console-only |
| `greenhouseWorker.js` → `saveErrorInfo()` | Same as Comeet — console-only |

### New Insights

| Area | v6.1 State | v6.2 State |

| **Session methodology** | Cursor-only debug/plan/apply cycle | Gemini external architect review → Cursor PLAN → Cursor APPLY → Cursor forensic investigation → Gemini deployment guidance |

### Behavior Changes

- **Silent dedup** — ATS workers now track `skippedDedup` in their stats. Jobs with IDs already in `ats_sent_history` are skipped before any normalization, filtering, or calibration write.
- **No `NODE_ENV` dependency** — `writeRunLog` behavior is identical across all environments. Local dev and production both route only summaries to DB.
- **Structured Gate** — Comeet worker now uses `evaluateStructuredGate()` (from `ats/filters/structuredGate.js`) as a fast-track gate before the regex-based ATS Guard. Jobs with `experience_level` matching seniority patterns are dropped early; student/intern jobs are whitelisted early.

### Key Findings from Forensic Investigation

The session included two rounds of forensic investigation (one by Cursor in this session, one in the previous debug context):
1. **First investigation** (Cursor debug) concluded that the `NODE_ENV` gate was the issue — local runs without `NODE_ENV=production` bypassed the guard.
2. **Second investigation** (this session, post-refactor) confirmed the local code was 100% clean. The **stale Cloud Run deployment** was identified as the sole source of ghost writes.

### Known Failure Modes

| Failure Mode | Symptom | Diagnosis | Resolution |
|---|---|---|---|
| **MongoDB quota exceeded** | `"you are over your space quota"` errors; duplicate emails resume | Check Atlas storage usage → Collections tab | Reduce TTLs; verify `calibration_rejected` is bounded |

| **Workday WAF block** | `403` or `0 jobs` from specific Workday companies | Workday anti-bot detection | Adjust `WORKDAY_DELAY_*_MS` env vars |
| **Comeet rate limit** | `429` responses | API rate limit hit | Increase `COMEET_DELAY_*_MS` env vars |
| **Persist failure** | Run crashes with `"Failed to persist sent history"` | Fail-fast throw from `persistSentHistory` | Check MongoDB connectivity and quota |
| **Stale Cloud Run deployment** | Zombie collections reappear after drop | Cloud Run running old image | Redeploy via `gcloud run jobs deploy jobbot-runner --source . --region europe-west1` from Cloud Shell |
| **Workday location facet** | `[WD WARN] No location facet found` / `facetId is invalid` | Workday's dynamic facet structure varies per tenant | Non-blocking — falls back to `searchText` filter |

### 1.2 State & Storage Overview

- **Mongo Collections** (unchanged from 2026-03-01 snapshot, but now fully leveraged for LinkedIn):
  - **`seen_jobs`**: LinkedIn dedup memory for `scraper.js` (`loadSeenJobIds()` / `saveSeenJobIds()`).
  - **`ats_sent_history`**: ATS cross-run dedup (`JobStateService`).
  - **`calibration_passed`**: Lightweight metadata of all jobs that passed final gates and were sent via email (ATS + LinkedIn).
  - **`calibration_rejected`**: Lightweight metadata of semantic/guard rejections (ATS + LinkedIn); TTL 60 days; now includes LinkedIn title-filter drops.
  - **`run_summaries`**: Per-run summaries for ATS and LinkedIn (`source: 'ats' | 'linkedin'`), TTL 30 days.

- **Filesystem Layout (relevant to this session)**:
  - `logs/linkedin/summaries/` & `logs/linkedin/filtered/`: legacy artifacts used by `tools/linkedin/analyze_logs.js` (now functionally superseded by Mongo-based calibration).
  - `output/test_calibration_report.md`: generated `.md` report from `services/calibration/calibrationReport.js` (used by `tools/test_calibration.js`).
  - `output/linkedin/`: legacy LinkedIn enriched jobs (no longer used as calibration source — now replaced by `calibration_passed`).

## 3. Core Achievements (Technical)

### 3.1 LinkedIn Semantic Drops → `calibration_rejected`

- **What changed**
  - In `scraper.js → runLinkedinScraper(options)`, the scraper now accumulates semantic title-filter rejections into a new in-memory buffer:
    - `const linkedinCalibrationDrops = [];`
  - On each enriched job, after `fetchJobDetails()`, LinkedIn still applies the **binary title filter**:
    - `if (!passesFilters(enrichedJob, runStats, filteredJobsLog)) { ... }`
  - Inside this `!passesFilters` branch, we now:
    - Log the drop as before.
    - Inspect the last entry in `filteredJobsLog` to recover the **semantic reason** (`'Blacklist'` or `'Whitelist'`).
    - Push a **lean calibration record** into `linkedinCalibrationDrops`:
      - `jobId`: `enrichedJob.jobId` (LinkedIn ID from Voyager/GraphQL).
      - `title`: job title.
      - `companyName`: `enrichedJob.companyName || company`.
      - `location`: `enrichedJob.location || 'Unknown location'`.
      - `url`: `enrichedJob.applyUrl || enrichedJob.url || null`.
      - `reason`: `'Blacklist'` / `'Whitelist'` (or safe fallback `'TitleFilter'` if the log entry isn’t aligned).
      - `gate`: `'linkedin_title'`.
      - `source`: `'linkedin'`.
  - In the `finally` block of `runLinkedinScraper`:
    - Before writing the run summary, the scraper now calls:
      - `await storage.writeCalibrationRejected(linkedinCalibrationDrops);`
        - This uses `MongoStorageAdapter.writeCalibrationRejected()`, which strips fields via `_stripJobForCalibration()` and inserts into `calibration_rejected` with `createdAt`.

- **Why it was done**
  - Previously, **LinkedIn semantic drops only existed in local log JSONs** (`filtered_jobs_debug_*.json`) and in the in-memory `filteredJobsLog` array. The Mongo-based calibration system could not see them.
  - The new calibration report uses `calibration_rejected` as the canonical source for semantic rejections. Without feeding LinkedIn into this collection, the “Rejected by Source/Gate” and exhaustive rejected lists were **ATS-only**.
  - Routing title-filter drops into `calibration_rejected` (with a dedicated gate `linkedin_title`) gives:
    - Unified Semantic Rejection heatmaps across ATS + LinkedIn.
    - Ability to segment LinkedIn gate performance and tune Blacklist/Whitelist safely.

- **Where in code**
  - `scraper.js`:
    - Buffer definition:
      - `runLinkedinScraper()` → `const linkedinCalibrationDrops = [];`
    - Semantic drop mapping:
      - In the loop where `enrichedJob` is created and `passesFilters()` is called:
        - On `!passesFilters(enrichedJob, runStats, filteredJobsLog)`, construct and push calibration records into `linkedinCalibrationDrops`.
    - Persistence:
      - In `finally { ... }`, before `writeRunLog`, guarded call:
        - `if (linkedinCalibrationDrops.length > 0) await storage.writeCalibrationRejected(linkedinCalibrationDrops);`

- **Impact / risk**
  - Impact:
    - **LinkedIn now appears in:** `Rejected by Source`, `Rejected by Gate` (via `gate: 'linkedin_title'`), and in the Exhaustive Rejected list.
    - Calibration collections remain lightweight (no raw HTML, no giant payloads).
  - Risks:
    - Over-reliance on `filteredJobsLog` ordering: we defensively fall back to `reason: 'TitleFilter'` if the last log entry doesn’t match, so calibration remains robust even if future logging changes slightly.

### 3.2 Excluding Dedup Noise (`alreadySeen`) from Calibration

- **What changed**
  - No behavioral changes to dedup logic; instead, **calibration wiring deliberately avoids dedup paths**:
    - Dedup still happens **before enrichment**:
      - `if (seenIds.has(job.jobId)) { ... continue; }`
      - This increments `runStats.filteredOut.alreadySeen` and appends `{ title, company, reason: 'AlreadySeen' }` to `filteredJobsLog`, but the job **never reaches** `passesFilters()`.
    - The new LinkedIn calibration buffer is only populated **inside the `!passesFilters()` branch**, which is only reached after:
      - The job is **not already seen**.
      - It has been fully enriched via GraphQL.
  - As an extra layer of defense, the semantic mapping code checks:
    - If the derived `semanticReason` equals `'AlreadySeen'`, it does **not** push a calibration record.

- **Why it was done**
  - `calibration_rejected` is explicitly defined to store **semantic/business logic drops** (title, department, seniority, location gates), **not mechanical dedup noise**.
  - Dedup noise was the primary cause of the runaway `calibration_rejected` growth in pre-v6.2 versions; this session protects LinkedIn from reintroducing that issue.

- **Where in code**
  - `scraper.js`:
    - Dedup: `seenIds.has(job.jobId)` block (unchanged).
    - Semantic calibration block only lives _after_ dedup and _inside_ `!passesFilters`.

### 3.3 LinkedIn Run Summary Enhancements (`run_summaries`)

- **What changed**
  - `scraper.js` already populates `runStats` with:
    - `startTime`, `status`, `totalQueries`, `rawJobsFetched`, `candidatesEnriched`, `newJobsAdded`, `repostsDetected`, `filteredOut.*`, `errors`, and per-query `queryLog`.
  - In `finally`, we now also compute:
    - `runStats.endTime = new Date().toISOString();`
    - `runStats.newJobsAdded = allNewJobs.length;`
    - `runStats.totalDurationMs = end - start` (only if timestamps parse and `end >= start`).
  - The run summary write:
    - `await storage.writeRunLog({ type: 'summary', source: 'linkedin', timestamp: logTimestamp, payload: runStats });`
    - continues to route into `run_summaries` with `createdAt` via `MongoStorageAdapter.writeRunLog()`.

- **Why it was done**
  - `tools/linkedin/analyze_logs.js` relied on filesystem `run_summary_*.json` files to compute:
    - Success rate, average run duration, quota hits, query yield, blacklist/whitelist counts, etc.
  - Those same metrics are now obtainable entirely from `run_summaries` (source `linkedin`), with `totalDurationMs` aligning with the existing ATS Operational Health report.

- **Where in code**
  - `scraper.js → runLinkedinScraper()`:
    - `runStats` initialization.
    - `finally` block duration calculation and `writeRunLog` call.
  - `services/storage/MongoStorageAdapter.js → writeRunLog()`:
    - Persists `payload` into `run_summaries` when `type === 'summary'`.

### 3.4 New Calibration Report Section: LinkedIn Search Efficiency

- **What changed**
  - In `services/calibration/calibrationReport.js`:
    - Added `const LINKEDIN_LOOKBACK_DAYS = 30;`.
    - Inside `generateCalibrationReportMd(storageAdapter)`, immediately after **Global Metrics**, we now emit:
      - `## LinkedIn Search Efficiency (Query Matrix)`
  - This section:
    - Loads recent LinkedIn run summaries:  
      - `sumCol.find({ source: 'linkedin', createdAt: { $gte: now - 30d } })`.
    - If none exist:
      - Renders `_No LinkedIn run summaries available in the selected window._`
    - Otherwise, computes in JS (mirroring `tools/linkedin/analyze_logs.js`):
      - **LinkedIn Run Health**
        - `totalRuns`, `successRuns`, `successRate`.
        - Average duration (from `startTime`/`endTime` per run).
        - `totalQuotaHits` (from `filteredOut.quotaHit`).
        - `totalQueriesRun` (sum of `totalQueries`).
        - `totalErrors`.
      - **LinkedIn Filtering Calibration**
        - `totalBlacklist`, `totalWhitelist`, `totalAlreadySeen`, `totalReposts`.
      - **Dead Queries (Matrix Calibration)**
        - Aggregates per-query from `payload.queryLog`:
          - For each `query`: `rawTotal`, `newTotal`, `runsWithData`, `zeroRawRuns`.
        - Dead Queries = `rawTotal === 0 && runsWithData > 0`, sorted by `zeroRawRuns`.
      - **Top Performers**
        - Same per-query data, filtered to `newTotal > 0`.
        - Sorted by `avgNewPerRun = newTotal / runsWithData`, top 5.
      - **LinkedIn Semantic Drops (Title Filter)**
        - Mongo aggregation on `calibration_rejected`:
          - `{ source: 'linkedin', gate: 'linkedin_title' }`
          - Group by `reason`, sort by count desc, limit 15.
        - Rendered as a markdown table or a fallback “no LinkedIn semantic rejections” message.

- **Why it was done**
  - This section **replaces `tools/linkedin/analyze_logs.js`** as the primary LinkedIn health report:
    - Same business metrics, but sourced from MongoDB instead of local JSON logs.
  - It keeps the ATS report clean:
    - Global metrics remain unchanged.
    - LinkedIn-specific analysis is grouped under a dedicated heading, not mixed into ATS tables.

- **Where in code**
  - `services/calibration/calibrationReport.js`:
    - Top-level constant: `LINKEDIN_LOOKBACK_DAYS`.
    - New LinkedIn section embedded in `generateCalibrationReportMd()` between **Global Metrics** and the existing ATS sections.

## 5. Configuration Snapshot

### 5.1 DAILY_NEW_JOBS_LIMIT (LinkedIn)

- **Value:** `500`
- **Source of truth:** `scraper.js`:
  - `const DAILY_NEW_JOBS_LIMIT = 500;`
  - Used to stop the LinkedIn search when enough **new enriched** jobs have been collected:
    - When `allNewJobs.length >= DAILY_NEW_JOBS_LIMIT`, the scraper:
      - Sets `quotaReached = true`.
      - Marks `runStats.filteredOut.quotaHit = true`.
      - Breaks out of the query/page loops gracefully.

### 5.2 Jitter / Delay Configuration

- **LinkedIn (`scraper.js`):**
  - Helper `randomDelay(minMs, maxMs)`:
    - Between search queries: `randomDelay(10000, 20000)` (10–20 seconds).
    - Between pages of a query: `randomDelay(3000, 7000)` (3–7 seconds).
    - Between `fetchJobDetails` calls: `randomDelay(3000, 6000)` (3–6 seconds).
  - **Behavior:** Hardcoded human-like jitter, not env-driven.

- **Comeet Worker (`ats/workers/comeetWorker.js`):**
  - `COMEET_DELAY_MIN_MS` / `COMEET_DELAY_MAX_MS`:
    - Default: 3000–6000 ms (3–6 seconds), overridable via env.
  - Used in a per-request `randomDelay()` wrapper to mimic user browsing and comply with WAF/rate limits.

- **Greenhouse Worker (`ats/workers/greenhouseWorker.js`):**
  - `GREENHOUSE_DELAY_MIN_MS` / `GREENHOUSE_DELAY_MAX_MS`:
    - Defaults: 6000–12000 ms (6–12 seconds).
  - Used between Greenhouse HTTP requests via `randomDelay(min, max)`.

- **Workday Worker (`ats/workers/workdayWorker.js`):**
  - `WORKDAY_DELAY_MIN_MS` / `WORKDAY_DELAY_MAX_MS`:
    - Defaults: 5000–6000 ms (5–6 seconds) for pagination.
  - Additional fixed delay:
    - `SESSION_INIT_DELAY_MS = 2000` ms between session init and first API call.

### 5.3 BLACKLIST_KEYWORDS / WHITELIST_KEYWORDS

- **Source of truth:** `filters_shared.js`:
  - `BLACKLIST_KEYWORDS`:
    - Large curated list (over 100 entries) of seniority, non-tech and irrelevant domains (e.g., “Senior”, “Manager”, “Marketing”, “Sales”, finance/legal roles, hardware-specific terms, Hebrew non-tech terms).
    - Includes Phase 5.2 and 5.3 updates (removal of the ambiguous `'STA'` and replacement with `'Static Timing'`, `'STA Engineer'`).
  - `WHITELIST_KEYWORDS`:
    - Positive indicators of technical roles (e.g., “Software”, “Developer”, “Engineer”, “Data Analyst”, “QA”, “DevOps”, “Frontend”, “Backend”, “Junior”, “Student”, “Intern”, etc.).
  - Exported as:
    - `module.exports = { BLACKLIST_KEYWORDS, WHITELIST_KEYWORDS, titlePassesSemanticFilters };`

- **Usage:**
  - **LinkedIn Binary Title Filter (`scraper.js → passesFilters()`):**
    - Drops any title containing a Blacklist keyword.
    - Drops any title that does **not** contain at least one Whitelist keyword.
    - Writes filter events into:
      - `runStats.filteredOut.blacklist` / `.whitelist`.
      - `filteredJobsLog` (used both for console debugging and now for calibration reasons).
  - **ATS Semantic Gate (`ats/utils/semanticGate.js` → `passesSemanticGate()`):**
    - Reuses `filters_shared.titlePassesSemanticFilters()` to align ATS semantic title logic with LinkedIn’s binary filter, ensuring a single source of truth.

## 6. Observability & Maintenance

### 6.1 How to Run Key Flows

- **LinkedIn Standalone Scraper**
  - **Command:**
    - `node scraper.js`
  - **Env flags:**
    - `DRY_RUN=true` → skip LinkedIn email (`sendJobReport`) but still write `run_summaries` (source `linkedin`) and `calibration_rejected` drops.
  - **Expected outputs:**
    - Console logs with per-query/page stats, enrich logs, and filter decisions.
    - Updated:
      - `seen_jobs` (dedup memory).
      - `run_summaries` (LinkedIn).
      - `calibration_rejected` (LinkedIn semantic drops, gate `linkedin_title`).

- **Unified Orchestrator (ATS + LinkedIn)**
  - **Command:**
    - `node ats/orchestrator.js`
  - **Common local testing patterns:**
    - **Full dry run, ATS only:**
      - `$env:DRY_RUN="true"; $env:SKIP_LINKEDIN="true"; node ats/orchestrator.js`
    - **Full dry run, ATS + LinkedIn:**
      - `$env:DRY_RUN="true"; node ats/orchestrator.js`
  - **Expected outputs:**
    - Combined ATS + LinkedIn dedup flow.
    - Calibration collections populated for both passes and rejections.

### 6.2 Calibration Report & Tools

- **Generate calibration report (no email)**
  - `node tools/test_calibration.js`
  - Produces:
    - `output/test_calibration_report.md` including:
      - Global metrics (all sources).
      - **LinkedIn Search Efficiency (Query Matrix)** section.
      - Rejected/Passed by Source/Gate.
      - Exhaustive lists for passes and semantic/guard rejections.

- **Legacy LinkedIn analyzers (now redundant)**
  - `tools/linkedin/analyze_logs.js`
    - Reads filesystem LinkedIn logs to produce a text report; kept mainly for historical debugging, not as a primary calibration tool.
  - `tools/linkedin/show_rejected_history.js` / `show_acc_history.js`
    - Inspect legacy JSON logs; again, superseded by Mongo collections and the calibration report.

### 6.3 Known Failure Modes & Diagnosis

- **LinkedIn Auth Challenges**
  - `linkedin_client.js`:
    - Uses `axiosClient` with `maxRedirects: 0`.
    - Any 302/303 response:
      - Triggers `sendCriticalAlert(...)`.
      - Throws `LinkedInAuthChallengeError`.
    - Orchestrator and scraper treat this as a hard stop; calibration system never writes partial/tainted data.

- **MongoDB Volume Pressure**
  - `MongoStorageAdapter.runVolumeCleanupProtocol()` and `calibrationReport.checkVolumeTrigger()`:
    - Already wired from previous phases.
    - LinkedIn now contributes semantically trimmed records, minimizing footprint while still enabling deep analytics.

## 3. Core Achievements (Technical)

### 3.1 ATS Configuration Schema Analysis

- **What:** Deep analysis of all 3 ATS workers to extract the exact data schema needed to configure a new company in our DB.
- **Why:** The Discovery LLM needs to know precisely what fields to return for each ATS so our workers can consume the company configs correctly.
- **Findings:**
  - **Comeet** needs: `id` (slug), `name`, `type: 'comeet'`, `uid` (hex-dot code, e.g. `"41.00B"`), `token` (32-char hex).
  - **Greenhouse** needs: `id` (slug), `name`, `type: 'greenhouse'`, `uid` (board slug, e.g. `"wizinc"`).
  - **Workday** needs: `id` (slug), `name`, `type: 'workday'`, `url` (full `*.myworkdayjobs.com` career site URL).
- **Where:** Analysis documented internally; schemas consumed by `promptTemplates.js` (ATS hints) and `mapToValidatorFormat()` in `run_discovery.js`.

### 3.2 ATS Validation Scripts (3 scripts)

- **What:** Three independent CLI/programmatic scripts that probe live ATS APIs to verify proposed company configs before DB insertion.
- **Why:** Prevents "garbage in" — the LLM may hallucinate company identifiers or return stale URLs. Validators perform real HTTP calls and check **response shape**, not just status codes.
- **Validation logic per ATS:**

| Script | Path | HTTP Method | Shape Checks |
|--------|------|-------------|--------------|
| Comeet | `tools/comeet/validate_companies.js` | GET → Comeet Careers API v2.0 | Array response, items have `position_uid` + `name` |
| Greenhouse | `tools/greenhouse/validate_companies.js` | GET → boards-api.greenhouse.io | `{ jobs: [...] }` with `id` + `title` per job |
| Workday | `tools/workday/validate_companies.js` | GET (session init) → POST (CXS search) | Cookie-jar session, `jobPostings` array with `title` + `externalPath` |

- **Common patterns across all 3:**
  - Input: `validateCompanies(Array<CompanyObj>)` → returns `{ approved: [], rejected: [] }`.
  - Per-company `try/catch` isolation (one bad company doesn't crash the batch).
  - Schema validation (required fields check) before HTTP call.
  - Content-Type verification (must be `application/json`).
  - Response shape spot-check (not just HTTP 200).
  - Exported as both CLI (`node tools/comeet/validate_companies.js '[...]'`) and module (`require()`).

### 3.3 Discovery Pipeline Design & Implementation

- **What:** A standalone Node.js automation (`tools/discovery/run_discovery.js`) that autonomously discovers, validates, and inserts new tech companies.
- **Why:** The Job Aggregation Engine was previously limited to a static list of companies manually added to the DB. This pipeline enables autonomous growth of the company pool.
- **Architecture decisions:**
  - **Node.js only** (no Python/DSPy) — preserves monorepo unity, avoids polyglot Docker images, simplifies Cloud Run deployment.
  - **Sequential ATS processing** (`for...of` loop) — keeps LLM prompts focused, avoids Perplexity rate limit issues.
  - **Reuse of existing infra:** `createStorageAdapter()` for MongoDB, `createEmailNotifier()` for reports, validation scripts via `require()`.
  - **Dry Run mode** (`DISCOVERY_DRY_RUN=true`) — executes full pipeline including LLM + validators, but skips DB writes.

### 3.4 Perplexity Sonar Refactor (Meta-Prompting Architecture)

- **What:** A major refactor of the Discovery Pipeline's LLM integration based on a "cheat code" document obtained by meta-prompting Perplexity itself.
- **Why:** The original implementation relied on prompt-level JSON enforcement ("return ONLY a valid JSON array") — a fragile "hope-based" approach. The Sonar architecture uses **API-level structural guarantees** that make malformed output physically impossible.
- **The meta-prompting technique:** We asked Perplexity (via browser) "what is the optimal prompt architecture for your own API?" — a technique called Meta-Prompting that extracts the model's own knowledge of its parsing behavior.

**Key changes:**

| Component | Before | After (Sonar) |
|-----------|--------|---------------|
| `perplexityClient.js` — temperature | `0.1` | `0` (fully deterministic) |
| `perplexityClient.js` — response enforcement | None (prompt-only) | `response_format: { type: 'json_schema', json_schema: {...} }` |
| `perplexityClient.js` — max_tokens | Not set | `4096` (prevents truncated JSON) |
| `promptTemplates.js` — system prompt | Generic "research assistant" | Role-anchored "Israeli tech industry analyst specializing in recruitment technology" |
| `promptTemplates.js` — ATS config | Per-ATS `schema` + `example` JSON | ATS hints only (URL patterns + field mapping instructions) |
| `promptTemplates.js` — user prompt | Simple flat template | Structured: EXCLUSION LIST → DISCOVERY INSTRUCTIONS → ATS CONFIG → CONFIDENCE LEVELS |
| `run_discovery.js` — JSON parsing | `extractJsonArray()` (regex-based fence stripping) | `JSON.parse()` directly (guaranteed valid by API) |
| `run_discovery.js` — normalization | `normalizeCompany()` (per-ATS fields expected) | `mapToValidatorFormat()` (universal → per-ATS mapping) |
| `run_discovery.js` — confidence | Not supported | `filterByConfidence()` drops `"unconfirmed"` |
| `run_discovery.js` — exclusion list | Array of `{ id, name }` objects | Flat array of company name strings |

**The mapping layer** (`mapToValidatorFormat()`) is the critical bridge:

| LLM Universal Field | Comeet Mapping | Greenhouse Mapping | Workday Mapping |
|---------------------|----------------|-------------------|-----------------|
| `company_name` | → slug `id` + `name` | → slug `id` + `name` | → slug `id` + `name` |
| `ats_identifier` | → `uid` (hex-dot code) | → `uid` (board slug) | Informational only |
| `ats_api_url` | Parse URL → extract `token` param | Not needed | → `url` field |
| `careers_page_url` | Informational | Informational | Fallback for `url` |
| `confidence` | Filtered upstream | Filtered upstream | Filtered upstream |

- **Where in code:**
  - `tools/discovery/perplexityClient.js` — `RESPONSE_FORMAT` constant (L22–53), payload construction (L88–93).
  - `tools/discovery/promptTemplates.js` — `SYSTEM_PROMPT` (L17), `ATS_CONFIGS` with `.hints` (L25–60), `buildUserPrompt()` (L73–99).
  - `tools/discovery/run_discovery.js` — `filterByConfidence()` (L42–52), `mapToValidatorFormat()` (L68–108), updated `processAts()` (L257–310).

## 6. Observability & Maintenance

### 6.1 How to Run Key Flows

- **LinkedIn Standalone Scraper** — `node scraper.js` (unchanged from baseline).

- **Unified Orchestrator (ATS + LinkedIn)** — `node ats/orchestrator.js` (unchanged from baseline).

- **Discovery Pipeline (NEW)**
  - **Dry Run (no DB writes):**
    - PowerShell: `$env:DISCOVERY_DRY_RUN="true"; node tools/discovery/run_discovery.js`
    - CMD: `set DISCOVERY_DRY_RUN=true && node tools/discovery/run_discovery.js`
    - npm: `npm run discover:dry` (requires `cross-env` installed).
  - **Full Run:** `npm run discover` or `node tools/discovery/run_discovery.js`.
  - **Expected console output:**
    - Per-ATS: existing company count → LLM response size → confidence filter stats → mapping log → validator results → DB insertion count.
    - Final summary: total suggested / validated / rejected / inserted + duration.
    - Email report (markdown attachment via `sendCalibrationAlert`).

- **ATS Validators (standalone testing):**
  - `node tools/comeet/validate_companies.js '[{"id":"test","name":"Test","type":"comeet","uid":"XX.00X","token":"ABCD1234"}]'`
  - `node tools/greenhouse/validate_companies.js '[{"id":"test","name":"Test","type":"greenhouse","uid":"test-slug"}]'`
  - `node tools/workday/validate_companies.js '[{"id":"test","name":"Test","type":"workday","url":"https://test.wd5.myworkdayjobs.com/TestCareers"}]'`

### 6.2 Known Failure Modes & Diagnosis

- **Perplexity cold start:** First request with a new JSON schema may take 10–30 seconds (documented in Sonar doc). Subsequent calls are fast.
- **Perplexity auth errors (401/403):** `perplexityClient.js` does **not** retry on auth errors — throws immediately with actionable message.
- **Comeet token extraction failure:** If the LLM returns a malformed `ats_api_url`, `new URL()` in `mapToValidatorFormat()` will catch and leave `token` empty. The Comeet validator will then reject the company during schema validation.
- **Workday session issues:** The Workday validator mirrors the worker's session-based approach (cookie jar + Akamai delay). WAF blocks will result in rejection, not crashes.
- **JSON truncation:** `max_tokens: 4096` provides generous headroom. If the LLM tries to return >15 companies (unlikely given prompt instructions), truncation would cause a `JSON.parse()` crash — caught by the per-ATS `try/catch` in `processAts()`.

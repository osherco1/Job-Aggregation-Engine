## 2. System Architecture View

**High-level data flow (unchanged from baseline, with new storage/calibration safeguards):**

- **Entry points:** `ats/orchestrator.js`, `scraper.js`, `run_bot.bat`. Orchestrator runs ATS workers (Comeet, Greenhouse, Workday) and LinkedIn in parallel, then dedup → email → persist → optional calibration trigger.
- **Volume trigger path (updated):** When `checkVolumeTrigger(storageAdapter)` (350 MB threshold) or 7-day time trigger fires, the orchestrator now:
  1. Generates a unique `ownerId` and calls **`acquireCalibrationLock({ ownerId, ttlMs })`** on `MongoStorageAdapter`. Only one process can hold the lock (atomic `findOneAndUpdate` on `system_state.calibration_lock`).
  2. If lock acquired: **report first** → **aggressive purge** → **email** (report → purge → email). If purge throws, email is never sent (fail-fast).
  3. In `finally`, **`releaseCalibrationLock({ ownerId })`** so the lock is always released.
- **State and outputs:** MongoDB `jobbot_db` (companies, seen_jobs, ats_sent_history, calibration_rejected, calibration_passed, run_summaries, system_state). Local: `data/*`, `docs/analyze/` for calibration reports. **New:** `tools/emergency_purge.js` bypasses report generation and runs `deleteMany({})` on calibration collections only, for use when the DB is over quota and the normal script would OOM.

## 3. Current Phase Status

**Current phase:** Post-incident stabilization; DB quota and calibration trigger hardened.

Production hit the Atlas 512 MB limit (517 MB in use). The previous logic (purge only `calibration_rejected` >7d, ignore `calibration_passed`, swallow errors, no lock) caused four “DB Volume Trigger” emails in three seconds and left the DB effectively unpurged. Implementation is complete: aggressive purge modes, distributed lock, strict report → purge → email order, fail-fast cleanup, and an emergency purge script. Emergency run deleted **655,066 + 738** records; a follow-up orchestrator run with `SKIP_LINKEDIN=true` completed successfully (181 jobs, 0 new after dedup).

## 4. Core Achievements (Technical)

- **Distributed calibration lock**
  - **What:** `MongoStorageAdapter.acquireCalibrationLock({ ownerId, ttlMs })` and `releaseCalibrationLock({ ownerId })` using atomic `findOneAndUpdate` on `system_state` document `_id: 'calibration_lock'`. Stale locks (e.g. `expiresAt <= now`) are stolen. Default TTL 15 minutes.
  - **Why:** Prevents multiple orchestrator processes from all passing the volume check and sending duplicate alerts (e.g. 4 emails in 3 seconds).
  - **Where:** `services/storage/MongoStorageAdapter.js` (lock methods); `ats/orchestrator.js` (ownerId, acquire before calibration, release in `finally`).

- **Aggressive volume purge and fail-fast**
  - **What:** `runVolumeCleanupProtocol(options)` accepts `{ mode: 'aggressive' | 'retention24h' | 'legacy7d' }`. For **volume** trigger the orchestrator uses **aggressive** only: delete all documents in `calibration_rejected` and `calibration_passed`. No try/catch around the purge; Mongo errors propagate.
  - **Why:** Legacy “>7d rejected only” purge did not free space when the spike was recent and never touched `calibration_passed`; swallowed errors allowed “success” emails despite failed deletes.
  - **Where:** `services/storage/MongoStorageAdapter.js` (`runVolumeCleanupProtocol`); `services/calibration/calibrationReport.js` (`runVolumeCleanup(..., { mode: 'aggressive' })` when `triggerType === 'volume'`).

- **Fixed execution order (report → purge → email)**
  - **What:** In `runCalibrationAndNotify()`: (1) generate calibration report from current DB, (2) `await runVolumeCleanup(..., { mode: 'aggressive' })` when volume-triggered, (3) send alert email with the pre-generated report. If step 2 throws, step 3 is skipped.
  - **Why:** Running purge before report would produce an empty report after aggressive delete.
  - **Where:** `services/calibration/calibrationReport.js` (`runCalibrationAndNotify`).

- **Emergency purge script**
  - **What:** `tools/emergency_purge.js`: connects with `MongoClient`, runs `deleteMany({})` on `calibration_rejected` and `calibration_passed` only. No report generation, no adapter stack.
  - **Why:** When the DB is over quota, `run_proactive_calibration.js --confirm` loads huge data for the report and can hang or OOM; emergency script frees space in seconds.
  - **Where:** `tools/emergency_purge.js`. Run: `node tools/emergency_purge.js`.

- **CLI and verification**
  - **What:** `run_proactive_calibration.js` with `--confirm` uses `runVolumeCleanupProtocol({ mode: 'aggressive' })` and logs `[AGGRESSIVE PURGE]`. Added `tools/verify_calibration_lock_and_purge.js` (lock acquire/release, exclusivity, stale lock steal, aggressive purge) and `npm run verify:calibration`.
  - **Why:** Align manual purge with orchestrator semantics; enable local verification of lock and purge behavior.
  - **Where:** `tools/run_proactive_calibration.js`, `tools/verify_calibration_lock_and_purge.js`, `package.json` scripts.

## 5. Contextual Delta (vs Previous Snapshot)

- **Baseline (snapshot_2026-03-08)** focused on proactive calibration CLI, discovery handoff, and DB quota awareness; it did not include a distributed lock, aggressive purge mode, or strict report-before-purge order.
- **New:** Volume trigger now uses a single-writer lock, mandatory aggressive purge for volume, and report → purge → email with fail-fast so no “success” email is sent if purge fails.
- **New:** Emergency path when DB is choked: `emergency_purge.js` avoids loading calibration data into Node and nukes the two calibration collections only.
- **Validation:** Post–emergency purge, orchestrator run (`SKIP_LINKEDIN=true`) completed (181 ATS jobs, run summary saved, no quota warning). Lock and purge logic are in place; `verify:calibration` can fail locally if Atlas is still over quota (e.g. “you are over your space quota”).

## 7. Observability & Maintenance

- **Unified orchestrator (ATS only for quick test):**  
  `$env:SKIP_LINKEDIN="true"; node ats/orchestrator.js`
- **Full orchestrator:**  
  `node ats/orchestrator.js` or via `run_bot.bat`.
- **Calibration report (dry run):**  
  `npm run calibrate:report` → report to `docs/analyze/`, no DB mutations.
- **Calibration purge (aggressive, with timer update):**  
  `npm run calibrate:purge` or `node tools/run_proactive_calibration.js --confirm`.
- **Emergency purge (no report, nuke calibration collections only):**  
  `node tools/emergency_purge.js`. Use when DB is over quota and the normal calibration script hangs or OOMs.
- **Lock + purge verification:**  
  `npm run verify:calibration` (requires MongoDB under quota for full pass).
- **Logs/outputs:** Run summaries in MongoDB `run_summaries`. TTL indexes: calibration_rejected/calibration_passed 60d, run_summaries 30d. Lock acquire/release and calibration trigger skip (lock held) are logged to console.
- **Known failure modes:**  
  Atlas over 512 MB can make writes (including lock upsert) fail or throttle; use `emergency_purge.js` first. Greenhouse 404 (e.g. Snyk, Redis) and Workday facet/422 errors are logged and do not stop the run. Calibration email is sent only after successful purge (fail-fast).

# Technical Infrastructure Snapshot — DB Quota Stability & Catch-22 Lock Fallback

**Date:** 2026-03-16  
**Scope:** Resolution of the DB 512MB quota explosion, implementation of the emergency lock fallback, and introduction of TTL bounds for historical data.  
**Baseline:** `snapshot_2026-03-12.md`

---

## 1. Executive Summary

The production database hit the strict 512MB Atlas M0 quota. This created a "Catch-22" scenario: the volume trigger fired, but `acquireCalibrationLock` failed because it required a DB write. The error was swallowed, causing the orchestrator to bypass the purge entirely, proceed to scrape, send an email, and crash during `persistSentHistory`. Cloud Run retried the job, causing an infinite loop of duplicate emails. 

This snapshot documents the implementation of an emergency lock fallback protocol, the fail-fast orchestration halt, and the introduction of TTL bounds to previously unbounded collections (`seen_jobs` and `ats_sent_history`).

---

## 2. System Architecture View (Updated)

**High-level data flow (Changes to Phase 0/5):**

- **Volume trigger path (Updated):** 1. `checkVolumeTrigger()` now measures `storageSize + indexSize` (not just `dataSize`) to accurately reflect Atlas billing metrics.
  2. Orchestrator attempts `acquireCalibrationLock()`.
  3. **[NEW] Emergency Fallback:** If `acquireCalibrationLock` throws an error (e.g., Quota Exceeded), the orchestrator catches it and forcefully triggers `runVolumeCleanupProtocol({ mode: 'aggressive' })` *without* a lock.
  4. **[NEW] Fail-Fast:** If the emergency aggressive purge also fails, the orchestrator rethrows the error, completely halting the run *before* Phase 1 (ATS Workers) or Phase 2 (LinkedIn Scraper) can begin. No ghost emails can be sent.
- **Storage Lifecycle (Updated):** `seen_jobs` and `ats_sent_history` are no longer permanent. They are now automatically pruned by MongoDB TTL indexes.

---

## 3. Core Achievements (Technical)

* **Catch-22 Lock Fallback (Orchestrator)**
    * **What:** Separated `try/catch` logic around `acquireCalibrationLock`. If it throws under volume pressure, an emergency purge is executed.
    * **Where:** `ats/orchestrator.js`.
* **Fail-Fast Orchestration Halt**
    * **What:** Purge failures now correctly bubble up to the top-level `Promise.allSettled` handler. If the DB cannot be cleaned, the bot will not scrape or send emails.
    * **Where:** `ats/orchestrator.js`.
* **Unbounded Growth Control (TTL Indexes)**
    * **What:** Added TTL indexes to previously unbounded collections in `_ensureTTLIndexes()`.
    * **Details:** `seen_jobs` (90 days / 7,776,000s), `ats_sent_history` (180 days / 15,552,000s).
    * **Where:** `services/storage/MongoStorageAdapter.js`.
* **Accurate Volume Metrics**
    * **What:** `getDbSizeBytes()` now calculates `stats.storageSize + (stats.indexSize || 0)`, falling back to `dataSize` only if `storageSize` is unavailable.
    * **Where:** `services/storage/MongoStorageAdapter.js`.

---

## 4. Contextual Delta (vs Previous Snapshot)

* **Baseline (snapshot_2026-03-12):** Introduced the calibration lock and aggressive purge, but failed to account for lock-write failures when the DB was already at 100% capacity.
* **New:** Lock failure no longer silently skips the purge. It triggers an emergency bypass.
* **New:** Database growth is strictly bounded. All active collections now have a defined TTL lifecycle.

---

## 5. Configuration Snapshot

* **TTL Configuration:**
    * `calibration_rejected`: 60 days
    * `calibration_passed`: 60 days
    * `run_summaries`: 30 days
    * **[NEW]** `seen_jobs`: 90 days
    * **[NEW]** `ats_sent_history`: 180 days
* **Volume Trigger:** 350 MB (`VOLUME_THRESHOLD_BYTES`) based on `storageSize + indexSize`.
* **Cloud Run Task Retries:** Reverted back to default (safe due to Fail-Fast execution).
